# Registro STRIDE — Mini Shop Security Lab

> **Entorno multi-OS del hito:** el código puede desarrollarse en Windows o Linux; el contenedor de referencia es Linux y Docker Compose, el objetivo y las herramientas de pentest se ejecutan dentro de Debian 13 XFCE en la VM del laboratorio. Los comandos de los runbooks se ejecutan desde esa VM y el objetivo es exclusivamente `http://127.0.0.1:5080` dentro del invitado.

**Estado:** registro del alcance Fase 1 y sus superficies intencionalmente vulnerables. Las filas describen escenarios y evidencia requerida; no equivalen a hallazgos con evidencia manual ya capturada. Los controles de Fase 2 siguen pendientes.

| ID | Categoría | Actor/condición | Activo y superficie | Escenario/impacto a evaluar | Evidencia de Fase 1 | Control esperado para Fase 2 |
|---|---|---|---|---|---|---|
| S-01 | Spoofing | Atacante sin cuenta; login distingue usuarios | Identidad/credenciales; `POST /api/auth/login` | Enumerar usuario válido y probar credenciales ficticias hasta acceder como ese usuario | Respuestas comparadas y conteo pequeño de intentos | Respuesta uniforme, hash bcrypt, límite y bloqueo, TOTP |
| S-02 | Spoofing | Cliente autenticado altera token | Identidad/rol; Bearer JWT | Token débil o algoritmo no seguro permite que Cliente se haga pasar por Admin | Token de laboratorio original/alterado y respuesta admin | RS256 fijado, validación issuer/audience/exp y refresh rotativo |
| T-01 | Tampering | Usuario controla búsqueda | Integridad de consulta/catálogo; `q` en búsqueda | SQLi blind permite alterar condición de consulta e inferir nombre de BD/tablas sintéticas | Baseline y retraso repetible; metadatos requeridos | EF Core parametrizado, whitelist y mínimo privilegio DB |
| T-02 | Tampering | Cliente A manipula ID | Integridad de carrito/pedido; rutas con ID | Modificar cantidad de un recurso propiedad de Cliente B | Request de A con ID de B y estado verificado de seed | Ownership por objeto y operación; ID derivado/validado en servidor |
| R-01 | Repudiation | Usuario niega cambio de producto/pedido | Trazabilidad de acciones; APIs de escritura | Sin eventos atribuibles no se puede reconstruir quién cambió recurso y cuándo | Confirmar si el laboratorio registra actor/acción/request ID; documentar brecha | Auditoría con actor, acción, objeto, timestamp y request ID; protección frente a alteración |
| I-01 | Information Disclosure | Visitante abre producto con comentario malicioso | Sesión de `cliente-xss` y contenido; comentarios/detalle | XSS persistente captura la cookie válida de un usuario ficticio y la envía a `/lab/collect` en la misma app | Persistencia, ejecución, request de captura y replay de sesión local | Encoding contextual, evitar HTML no confiable, CSP y flags de cookie |
| I-02 | Information Disclosure | Cliente A cambia ID de carrito/pedido | Datos de Cliente B; rutas de lectura | BOLA revela contenido sintético de otro cliente | Request de A que devuelve recurso de B | Autorización por recurso/owner, deny-by-default |
| I-03 | Information Disclosure | Solicitante no autenticado compara respuestas | Registro de usuarios; login | Mensaje/status/tamaño/tiempo permite inferir qué cuentas existen | Comparación controlada válida/inválida | Respuestas uniformes y límites de intentos |
| D-01 | Denial of Service | Solicitante automatiza login | Disponibilidad del login | Ausencia de límite permite volumen de intentos y consumo desproporcionado | Solo demostrar ausencia de limitación con volumen pequeño; no probar estrés | Rate limit distribuido, lockout con recuperación y monitoreo |
| E-01 | Elevation of Privilege | Cliente llama endpoint admin o presenta token forjado | Funciones Admin; `/api/admin` | La app acepta rol suministrado por cliente o token alterado | Request como Cliente y comparación con Admin/token alterado | Policies RBAC y autorización server-side por endpoint/objeto |

El registro contiene más de ocho amenazas y cubre todas las clases STRIDE. Los casos I-02 y E-01 separan divulgación de datos y elevación de privilegio aunque compartan endpoint/IDOR. El detalle de pruebas está en [`../docs/fase1/ataques/`](../docs/fase1/ataques/) y las reglas de ejecución en [`../docs/fase1/procedimiento-pentest.md`](../docs/fase1/procedimiento-pentest.md).
